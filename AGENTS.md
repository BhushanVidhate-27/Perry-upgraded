# Project agent rules

## Package manager

- Use `pnpm` for installs, scripts, and package commands. Do not use npm or npx.

## Verification

- Prefer end-to-end tests as the primary mechanism for complex features. End each E2E run with a verifiable, repeatable artifact.
- Do not bolt on a `*.test.ts` after the fact just to assert code you just wrote. That is the one thing never to do: a test added to prove the code works is not a check, it is a witness.
- New non-trivial logic — a branch, a loop, a parser, money or security, or a whole new script or app — does leave a check behind: one small test or an assert-based self-check that fails when it breaks. One good check, not coverage. Write down every way it could fail before writing it, and keep it next to the logic it guards.
- The two together: E2E for how a feature behaves, and a small pre-written check for the risky logic inside it. A feature needs both; neither substitutes for the other.

## Development

- Find what already solves the problem before writing code. Read the source of the runtime, framework, and installed libraries before concluding a feature is missing.
- Prefer native platform features, then existing library utilities, then a few lines of project code, then a new abstraction, and only then a new dependency.
- Avoid keeping state that the platform already keeps. Replace clever custom behavior with the built-in equivalent when available.

## Next.js

- Before writing Next.js code, read the relevant guide in `node_modules/next/dist/docs/`, the docs bundled with the installed Next.js 16. Heed deprecation notices.
- Do not remove any Next.js agent-rules block generated by `next dev`. Check `node_modules/next/dist/server/lib/generate-agent-files.js` when it exists; a generated block will return if removed.
